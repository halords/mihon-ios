## Import-then-login adoption fix (2026-11-11)

- Root cause: signInAccount ran addDeviceLibrary() only when the server reported hasSyncedData === false (brand-new accounts). connect() swaps the live stores to the account profile, so for an established account the guest import stayed stranded in its profile snapshot, reachable only via the manual "Add your existing device library" button on the Account page. createAccount already adopted unconditionally; recoverAccount never adopted.
- Fix (src/lib/account.ts): sign-in and recover now pull the account's cloud state first, then ALWAYS addDeviceLibrary() (no-ops without a snapshot; merges via the backup-import path; consumes the snapshot), then sync again so the merged library uploads in the same session. ## Restore performance restructure (2026-11-10 evening)

- `restoreTachibk` no longer runs the whole backup in one IndexedDB transaction. A 60k-chapter backup issues ~160k writes plus one sync journal entry per write; as a single transaction nothing was durable until the end, a backgrounded/killed phone tab rolled the entire restore back to zero, and sync upload could not begin until everything finished. Now: existing chapter state/history are read once up front (keys embed their manga key, so the maps stay valid across transactions), categories commit in their own transaction, each title restores in its own transaction (only the in-flight title rolls back on failure), and the backup-level metadata + retained archive land in a final transaction so an archive row always means a completed restore. Re-running an interrupted restore is safe — all merges are idempotent — and per-title commits fire the sync-dirty signal, so account upload starts while later titles still restore.
- The history pass no longer re-puts every chapter state just to bump `lastReadAt`: the newest history read time per chapter URL is folded into the single chapter-pass state write (a guarded fallback still bumps pre-existing states of history-only chapters). That removes ~20k state writes (plus their journal entries) from a large restore.
- The old rollback test asserted all-or-nothing semantics and was rewritten for the new contract: completed titles + categories persist after a mid-restore failure, archives stay absent, and a re-run completes the import. ## Sync ack fix (2026-11-10, post-acceptance)
Acceptance timing on the revised pipeline: 131,039 changes uploaded in ~14–15 min (~150/s) — 3–5× the old build, short of the <3 min target. Root cause: `acknowledgeChanges` ran `syncRecords.getAll()` after EVERY batch (full 130k+ record deserialization, chapter payloads included, × ~33 batches). Fix (account.ts only):

- `summary()` and `cycle()` no longer materialize the whole store via getAll(); a cursor stream (`scanSyncRecords`) counts/collects pending in primary-key order (sequence unchanged). Caveat: still O(n) streaming — a by-pending index would need a db.ts schema bump.
- New tests: ack against a 5,000-record unrelated backlog with getAll rigged to throw (syncRevision), migration replace-vs-keep pair (tests/migration.test.ts — replace journals a library tombstone; keepOriginal=true keeps both).

## Download force-through (2026-11-10, user reports from Mangakakalot bulk downloads)
User's queue filled with 'Image download failed (HTTP 503)' and 'The source did not return a valid image' failures needing manual retries. Same root cause family: throttling (503 = explicit refusal; valid-image = CDN answering with an HTML block page as HTTP 200 once flagged).
- downloads.ts: page attempts 3 → 6, backoff 500/1000/2000/4000/8000 ms. On valid-image/empty-image failures the next attempt fetches a cache-busted URL (`_r=N` in the query part only; `#hash` preserved byte-identical for Asura #tiles=; cache identity still keyed to the original URL). Decode-skip: when the source supplies page width+height, imageDimensions() is not run (bulk-download CPU/heat reduction).
- downloadQueue.ts: transient chapter failures auto-requeue up to 2 times (attempts/notBefore on the job record) — 5s/15s cooldowns normally, 60s/180s for HTTP 429/503 (rate limits must be waited out, not hammered). Non-transient (storage full, title removed, no pages, too many pages, no image URL) fails immediately. Queue waits inside processQueue for the earliest due retry (250ms ticks, bails on pause/offline); manual retry / re-enqueue resets attempts.
- images.ts: imageMime extended — BMP, ICO, TIFF, HEIC/HEIF, JPEG XL; validateImageBlob falls back to a real decode attempt when magic bytes are unknown, accepting anything the browser can decode (user: pages can be GIFs or any browser-compatible format).
Suite: 122/123 (only pre-existing browserBackend VPS failure). Build clean.

## Clear queue fix (2026-11-10, user report)
'Clear queue' only removed one chapter. Old clearDownloadQueue looped removeDownloadJob per job — each call also ran that chapter's partial-page cleanup, and the first throw/hang aborted the loop (the page's action() swallowed the error into a toast), stranding the rest. Rewritten: pause, abort the in-flight download without awaiting it, delete ALL job rows in one transaction, refresh, then per-job page cleanup each wrapped in try/catch so one failure can't stop the others. Tests: tests/clearQueue.test.ts (clears all + cleanup called per job; one throwing cleanup still clears everything). Suite 124/125 (pre-existing browserBackend only).

## Live library updates (2026-11-12, user request)
User report: the Library did not reflect anything until the refresh button was tapped — finished chapters kept their old downloaded/unread counts, and a newly opened book stayed in its old position. Fix is live UI patching, local only: no sync traffic, no backend writes (the open-time sync still owns the database), and background sync still never reshuffles the visible Library.
- New `src/lib/libraryLive.ts`: tiny in-memory event bus (`subscribeLibraryLive`/`emitLibraryLive`) with four update types — `chapter-progress` (reader, after each progress save; carries the saved history record, read flag, auto-delete flag), `title-opened` (nav.openManga/openReader), `library-added`/`library-removed` (details page).
- New `src/lib/libraryData.ts`: `loadLibrary` moved here from the page (now also returns `history` so patches can recompute the resume card); `loadLibraryItem` targeted single-title load via by-manga indexes; `findResume` extracted; `applyLibraryLiveUpdate` surgically patches one title (counts recomputed from its chapters + shared state/download maps, so re-applying the same update is harmless); snapshot store (`get/set/subscribeLibrarySnapshot`) with a module-scope live subscription chained through a promise queue so patches serialize and the snapshot stays fresh even while the Library tab is unmounted.
- `LibraryPage.tsx` now reads the store via `useSyncExternalStore`; its hook only owns the full-reload path. `ReaderPage.tsx` flush emits `chapter-progress` after a successful save (only then, so the snapshot never runs ahead of IndexedDB); `maybeAutoDeleteReadChapter` now returns boolean (deleted or not). Newly added titles sort first under the default Last-read sort (`sort.read` = add time; `lastRead` stays honest 0 so the Started filter is unaffected) — session-only, a full reload re-derives it from real history.
- Tests: tests/libraryLive.test.ts (6: finish-chapter counts + resume advance + idempotency, unfinished-progress last-read bump, title-opened ordering, library-added first + targeted loader, library-removed, emit→snapshot wiring); autoDeleteRead asserts the boolean return. NOTE: `beforeAll` seeding does not survive into tests in this setup — seed per test (no other test file uses beforeAll with the DB). Suite 136/137 (only pre-existing browserBackend VPS failure). Build clean.
